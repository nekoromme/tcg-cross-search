# 通信量の上限（v0.8.2）

店舗が保証する許容回数ではなく、個人用の暴走防止設定。拒否・混雑があれば、この回数より少なくても接続できない。

## 登録と巡回

- 合言葉で開く監視領域ごとに最大10条件・50商品ページ。同じ商品でも別店舗のURLは1ページずつ数える。
- 旧版の51件以上のデータは削除せず、超過した有効ページを待機させる。
- 指定間隔、対象ページ数×86400÷8000秒、同じ店舗のページ数×86400÷1200秒の最大値を商品ごとの確認間隔に使う。通信時間と巡回待ちが加わるため、設定値どおりの検知時間は保証しない。
- 新規掲載の検索間隔は30分と「有効な条件・店舗の組み合わせ数×4通信×86400÷4000秒」の大きい方。4通信は負荷を分散するための目安。実通信の上限は別途強制する。
- 例：10ページで同じ店に1ページずつなら108秒以上。50ページで1店に5ページずつなら540秒（9分）以上。同じ店に10ページなら720秒（12分）以上。
- 手動検索は1画面で1商品、最大6店舗の取得を並列に実行。別タブとの合計も次の共有上限で制限する。

## サービス全体の強制上限

| 対象 | 上限 |
|---|---:|
| 手動＋自動の店舗への外部通信 | 20,000回／日 |
| うち自動監視 | 12,000回／日 |
| 同一ホスト（wwwの有無は統合） | 2,000回／日 |
| 全体の直近60秒 | 180回 |
| 同一ホストの直近60秒 | 30回 |
| 全体の同時接続 | 24本 |
| 同一ホストの同時接続 | 4本 |

日次は日本時間0時に切り替える。HTTP転送も1回ずつ計上。接続失敗も回数に含め、通信枠確認・保存に失敗した時は店舗に接続しない。外部通信前に回数を保存するため、異常終了による過少計上はしない。許可後に外部通信へ到達しなかった場合は保守的に消費扱い。保存や表示更新・Discord通知はこの店舗通信回数に含まないため、Cloudflare全体の利用料金上限を保証するものではない。

Cloudflareでは同じDurable Objectクラスの専用保存領域で全端末・全監視領域を直列に判定。内部操作用パスはWorkerの公開ルートに用意しない。接続枠は本文読了・例外時に解放し、異常終了時は45秒で失効する。

Node.js移行先でも同じ判定を使い、専用ファイルを同期・置換して保存する。1保存先につき1プロセスを守る既存の起動ロックを維持。Cloudflareと移行先を同時稼働した場合は回数を共有しないため、移行前に旧環境を停止する。

## 上限に達した場合

検索済みの結果を残し、未確認位置を継続タスクとして保持。未確認を在庫なしと扱わず、画面に上限待機の理由を表示する。手動検索の追加確認ボタンは待機時間後に再び有効になる。自動監視は次回予定を再開可能時刻に移す。在庫・通知の履歴は変更しない。

132テストで、回数・接続数・日付境界・別端末相当の同時要求・保存失敗・転送・上限後の再開情報・旧データ保持を含めて確認。
