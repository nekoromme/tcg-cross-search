# BOX横断検索・定価付近の在庫通知ロードマップ

作成日: 2026-09-07 / 基準バージョン: v0.3.0

この文書は開発計画。定期監視・通知はまだ実装・有効化していない。
各段階を別の作業として実装・検証し、完了状況と残った問題をここへ追記する。
閾値・巡回間隔は以下の推奨初期案で、確定した利用者設定ではない。

## 目標と対象

- 気になった商品を検索し、新品の日本語版1BOXを同じ条件で比較できる。
- ポケモンカード、ONE PIECEカードゲーム、ガンダムカードゲーム、ドラゴンボール、ロルカナについて、商品ごとのメーカー希望小売価格と比較する。
- 定価付近以下で購入できる在庫が新たに見つかった時に通知する。
- ドラゴンボールの初期対象はフュージョンワールド。別シリーズや海外版を混同しない。
- カートン、複数BOXセット、単品パック、シングル、オリパ、中古、空箱、用品は通常の通知対象外。
- 初期台帳は新商品・直近商品と実際に登録店で扱う商品から着手し、過去のBOXへ順次拡張する。未調査分を含めて「全BOX対応済み」と表示しない。
- 抽選監視リポジトリとは実行設定・状態・認証情報を分離する。抽選監視の通知先やスケジュールを流用・変更しない。

## 現状と優先順位

v0.3.0ではBOX表示、価格順、単位・在庫フィルター、要確認欄、表示設定保存まで対応済み。
19売り場の検索先頭ページから最大8候補、最大4件の詳細だけを調べている。
今の検索結果をそのまま定期通知へつなぐには、商品の特定・取りこぼし・状態判定に不足がある。

優先する改善:

1. 商品・販売単位・価格・在庫の正確な特定。失敗を売り切れ扱いしない。
2. 商品ごとの定価台帳と同一商品への対応付け。
3. 店舗別の取得範囲、未確認の件数、最終確認時刻を明示。
4. 条件内の在庫変化だけを通知し、通知の重複と故障時の沈黙を防ぐ。
5. お気に入り、同一商品の店舗別比較、価格履歴、送料表示。
6. 買取価格との比較は別の追加機能として扱う。定価以下と利益が出ることは同義ではない。

## 定価台帳の設計

### 保存する項目

| 項目 | 意味 |
|---|---|
| 商品識別子 | タイトル名＋商品番号＋言語＋商品形態。別シリーズを統合しない |
| 正式名・別名 | 日本語名、英語名、型番、よく使われる略記 |
| 商品コード | BOX用JANとパック用JANを区別して保存。番号だけで単位を決めない |
| 発売日・版 | 再販や仕様違い、価格改定の対象を区別する |
| 定価（税込） | メーカーの税込BOX希望小売価格を優先 |
| BOX入数 | パック価格から計算する際の1BOXあたりのパック数 |
| 根拠 | メーカー価格のURL、入数のURL、確認日、BOX直接価格か計算値か |
| 確認状態 | 確認済み・資料不足・価格改定要確認。未確認商品は自動通知しない |

公式にBOX価格がなければ「税込1パック価格×確認済み入数」で比較基準を作る。
入数の確認元がメーカー以外の場合は販売店等の出典も保存し、推定で入数を埋めない。
「メーカー希望小売価格」は販売価格の上限を強制するものではなく、このツールでの比較基準。
店舗の定価・通常価格・参考価格欄だけを根拠にしない。
文字列のあいまい一致だけで商品を確定せず、型番、正式名、言語、単位の証拠を合わせる。
ハイクラス、通常弾、特別弾、海外版、限定セットは別商品として扱う。
新弾の公式発表を低頻度で確認して台帳追加候補にし、確認が済むまで監視対象にしない。

## 価格と通知の初期設定案

### 価格判定

- 仮の標準設定は「税込商品価格がBOX基準価格の105%以下」。定価以下も含む。
- 設定は「定価以下のみ」「定価＋5%以内」「定価＋10%以内」「商品別の上限円」に変更可能にする。
- 5%は運用上の初期案であって、市場の割安さを保証する基準ではない。
- 例: 基準価格6,000円なら5%設定で6,300円まで、6,301円からは通知対象外。
- 閾値を超える掲載商品は通知対象から外すが、ページ自体は追跡候補として残す。値下げで条件内になった変化も検知する。
- 通知可否の基本判定は商品価格。送料が判明したら別欄に税込支払総額を表示し、送料不明は「未確認」とする。
- 送料込み上限を利用者が選んだ場合は、送料未確認の商品を自動的に上限内としない。
- 複数購入による送料無料、クーポン、ポイント、会員限定価格を無条件の値引きとして含めない。
- 予約受付は即納在庫と分離し、初期の在庫通知では予約を対象外とする案。予約通知は別に有効化できるようにする。
- シュリンクなし等は条件を表示。新品BOXと同じ扱いにするかは明示的な設定にする。初期の通常通知は外装条件を確認できたものを優先する。

### 通知する変化

1. 売り切れだった商品が、価格上限内の在庫ありになった。
2. 在庫はあったが高かった商品が、値下げされて価格上限内になった。
3. 新しく発見・確認できた商品ページに、条件内の在庫がある。

初回起動時は現在の状態を基準として保存し、既存の安値商品で通知を大量発生させない。
初回に見つかった条件内在庫は一覧として確認できるようにする。
在庫がある状態のまま、数が増減しただけでは繰り返し通知しない。
通信失敗・取得拒否・判定不明・一時的なページ消失を「売り切れ」として状態を上書きしない。
候補検知時には対象商品ページを追加確認し、検索結果の断片だけで送信しない。
送信済みイベントを保存し、同じ実行の再試行で同じ通知を繰り返さない。
通知サービス側の応答が不明な場合の重複リスクも診断ログに残す。完全な一度だけ送信を無条件に保証しない。

## 実行場所と通信量

最初は現在の構成を活用する。

- Cloudflare: 手動検索画面、比較表示。監視登録をWeb画面から変更する機能は本人認証を用意してから追加。
- GitHub Actions: 価格検索専用リポジトリで定期確認、検証、状態比較、通知を実行する初期案。
- 一回ごとの取得・解析処理は共有しつつ、手動検索と定期監視の入口・状態・実行時間を分ける。
- 監視のたびに既存の19店検索を呼ばない。登録済み商品ページの直接取得を中心にする。
- 新商品ページの発見は別の低頻度処理にする。初期案は1日1回、取り扱いゲーム別の売り場を巡回。
- 高値のページは削除せず低頻度で再確認。お気に入りや注目する新弾だけ頻度を上げる。
- 初期は30分ごと。必要性が確認できた対象だけ15分などに調整する。店側の制限と実測負荷を優先する。
- 店舗ごとの同時アクセスを制限し、失敗時は待ち時間を伸ばす。403/429や認証・人間確認を回避しない。
- 取得するページ数、同時接続、1実行の時間、再試行数、保存量に上限を置く。

計算例（商品ページを各1回取得する場合、追加確認・新規発見・再試行は別）:

| 監視対象 | 間隔 | 店舗ページへの通信/日 |
|---|---|---:|
| 3店にまたがる計10商品ページ | 30分 | 10×48 = 480回 |
| 計100商品ページ | 30分 | 100×48 = 4,800回 |
| 計100商品ページ | 15分 | 100×96 = 9,600回 |

これは店への通信回数。GitHub Actionsの実行時間やCloudflareの受信回数とは別の単位。
GitHubから店を直接取得する設計なら、その取得は既存Workerの1日10万受信回数には加算されない。
ただし、既存Worker経由の監視に変えた場合やCloudflareの保存サービスを使う場合は別途計算が必要。

[GitHubの公式説明](https://docs.github.com/ja/actions/reference/workflows-and-actions/events-that-trigger-workflows)では、定期実行は最短5分だが、混雑で遅延・実行取り消しがあり、公開リポジトリは60日間活動がないと定期実行が無効化される場合がある。
したがって、秒単位の再入荷争奪戦を保証する仕組みとして扱わない。取り逃しが実際に問題になった段階で、[Cloudflareの定期実行](https://developers.cloudflare.com/workers/configuration/cron-triggers/)等への移行を比較する。

### 状態保存・管理の注意

- 公開価格や在庫の状態はコードと独立して保存。GitHubの状態用ブランチを使う場合、Cloudflareのビルド対象からそのブランチを除外する。
- 状態更新や履歴追加のたびにアプリ全体を再公開しない。監視状態の書き込みは同時実行による競合を防ぐ。
- 通知先の認証情報はこの価格検索リポジトリ専用のSecretへ保存し、公開コード・ログ・状態ファイルへ出さない。
- 通知先は専用のDiscordチャンネルを初期案とする。実装時に用意する必要がある場合のみ、利用者へ認証情報の登録手順を案内する。チャットに秘密のURLを貼らせない。
- 個人的な監視リストや配送先条件は公開データとして保存しない。画面から変更する前にアクセス制限と非公開保存を設計する。
- Cloudflareのビルド設定や新しい保存先の作成にアカウント側の操作が必要なら、必要な設定値を準備してから手作業を依頼する。

## 故障が分かる仕組み

- 最終実行時刻、店ごとの最終成功時刻、調べた商品数、条件内件数、未判定件数、処理時間を記録する。
- 原因を「通信」「ページ構造」「商品特定」「価格」「在庫」「通知送信」で切り分ける。
- 連続失敗で監視が役に立たなくなった場合は、商品入荷通知とは別の運用警告を1回にまとめる。
- 別の起動経路で最終実行時刻の古さを確認する案を段階5で検討する。停止した監視処理自身だけに停止通知を任せない。
- 通知なしで「送るはずだった通知」を確認できる試運転モードを用意する。
- 代表的な実ページの必要最小限の検証データを保存し、店の構造変更による再発をテストで検知する。個人情報・認証情報・不要なページ全文を公開しない。
